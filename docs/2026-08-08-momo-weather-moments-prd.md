## 问题与机会

当前 Momo 已能显示 Agent 状态、同步多 GIF、响应点击并记录任务成果，但它对用户所处的现实环境没有反应。长时间处于桌面或佩戴场景时，宠物容易退化成“状态屏”：信息准确，却缺少偶发、低打扰、与当下有关的陪伴感。

普通天气页会与手机和手表系统功能同质化。机会是让天气只作为宠物行为的环境输入，不把 Momo 变成天气仪表盘：天气变化触发短时氛围，用户可用一次点击完成轻量照顾，然后宠物回到原有 Agent/自主状态。

## 目标用户

- 把 SF32LB52 设备放在桌面或佩戴，并使用手机/桌面伴侣同步 Agent 状态的开发者。
- 希望宠物有环境感，但不愿维护复杂饥饿、清洁、生病数值的用户。
- 重视隐私，希望位置留在手机端、固件不直接联网的用户。

## 产品目标

1. 用户无需打开手机，就能在 3 秒内理解 Momo 对当前天气的反应。
2. 每次明显天气变化最多提供一次可点击互动，形成“环境变化—宠物反应—用户照顾—即时反馈”的闭环。
3. 不传输原始位置，不在设备保存天气服务凭据，不让固件直接访问公网。
4. 不干扰 Agent 状态、待输入/错误提示、远端表情、打字动画和 GIF 传输。

## 非目标

- 不做完整天气应用、逐小时预报、地图、城市列表、空气质量或灾害预警。
- 不在固件端定位、联网、解析第三方天气 API 或保存 API key。
- 不传经纬度、城市、地址、SSID 或其他位置标识到设备。
- 不新增第三方图片、字体、音频；不复制来源项目任何素材。
- 不为天气硬编码现有 5 个 GIF 槽位含义，也不改变其传输协议兼容性。
- 不加入惩罚、死亡、连续签到焦虑或高频通知。

## 创意描述

手机伴侣在用户明确授权后获取天气，并只向设备发送一个最小快照：天气类别、温度、观测时间、有效期和序列号。设备把快照映射成非阻塞的 LVGL 氛围层和一句短提示：

| 天气类别 | 默认氛围 | 点击互动 | 完成反馈 |
|---|---|---|---|
| 晴朗 | 柔和光点/暖色光晕 | “和 Momo 晒会儿太阳” | 小幅摇尾或星光 |
| 多云 | 缓慢浮云形状 | “拨开一朵云” | 云层淡出一次 |
| 雨/雪 | 少量下落线段/雪点 | “替 Momo 挡一下” | 顶部形成短时遮罩并眨眼 |
| 炎热 | 暖色呼吸环 | “给 Momo 扇扇风” | 呼吸环转冷色后淡出 |
| 寒冷 | 冷色轻抖提示 | “暖暖 Momo” | 轻抖停止并出现暖色光点 |
| 雷暴/未知 | 不制造惊吓；仅显示中性提示或不显示 | 无强制互动 | 自动回到默认状态 |

所有效果首版由 LVGL 基本对象和现有宠物动画组合，不新增版权素材。若伴侣端已经为某个天气配置了 GIF 映射，它可以使用既有远端 `PLAY/RESTORE` 能力，但固件天气状态不依赖该映射。

## 核心场景与流程

### 场景 A：首次授权并同步

1. 用户在伴侣端开启“天气陪伴”，阅读位置只在手机端用于查询天气的说明。
2. 手机获取天气并生成最小快照；原始位置和服务凭据不进入 BLE 数据包。
3. 设备校验枚举、温度、时间、有效期和序列号，在 RAM 中替换旧快照。
4. 宠物页空闲且没有更高优先级事件时，显示当前天气氛围；不弹出模态框。

### 场景 B：天气发生明显变化

1. 伴侣端只在类别变化或温度跨过热/冷阈值时发送新序列。
2. 设备在下一次 UI 安全刷新中切换氛围，并显示不超过 4 秒的短提示。
3. 用户点击宠物，执行一次对应照顾互动；同一序列重复点击不重复记账或刷动画。
4. 完成反馈结束后进入 3 小时冷却；氛围可保留，互动提示不再打扰。

### 场景 C：Agent 或远端表情抢占

1. 收到 `NEEDS_INPUT`、`ERROR`、远端 `PLAY` 或打字动画时，天气提示和互动入口立即暂停。
2. 天气状态仍留在 RAM，不创建新的 LVGL timer 或后台动画。
3. 高优先级状态 `RESTORE` 或结束后，若快照仍有效，则恢复当前氛围；已过期则恢复普通宠物。

### 场景 D：断网、拒绝权限或数据过期

1. 伴侣无法取得天气时不发送伪造默认值，也不反复提示用户。
2. 设备在快照过期后 10 分钟内淡出天气氛围，回到普通宠物。
3. 重启后天气状态默认为未知，等待下一次伴侣同步；MVP 不写 Flash。

## 功能范围

### 伴侣端

- 显式开关、权限说明和最近同步状态。
- 将位置限制在伴侣进程内，只上传天气类别、温度、观测时间和有效期。
- 天气类别归一化为固定枚举，过滤服务商特有文案和图标。
- 类别变化、阈值跨越、连接恢复或最长 60 分钟刷新时发送；禁止分钟级高频 BLE 写入。
- API key 使用平台安全配置，不写入固件、日志或公开仓库。

### 固件端

- 固定大小天气快照、严格校验、序列去重、TTL 过期和诊断计数。
- 在现有 BLE worker 路径处理状态更新；GATT 回调不操作 LVGL、不写 Flash。
- 在宠物页面自己的 LVGL 生命周期中创建/销毁氛围对象，所有 UI 更新只发生在 GUI 线程。
- 复用现有点击入口，但天气互动只改变本地表现，不批准、拒绝、完成或修改远端 Agent 任务。
- 提供编译期开关和运行时关闭路径，关闭后完全恢复当前宠物行为。

## 状态与优先级

从高到低：

1. 安全/传输错误和固件升级等系统级阻断状态。
2. Agent `NEEDS_INPUT`、`ERROR` 和等待授权提示。
3. 远端打字动画与明确的 `PLAY(slot)` 表情请求。
4. Agent 运行/完成表现及任务花园待领取反馈。
5. 天气陪伴互动和氛围。
6. 默认宠物待机。

天气层只能装饰或短时补充，不得覆盖更高优先级文字，不得重定义 GIF 槽位。高优先级状态结束时根据最新有效快照重新计算，不回放已错过的天气互动。

## 数据契约假设

正式字段编号由技术方案分配，本 PRD 只定义语义：

- `schema_version`：协议版本。
- `sequence`：伴侣端单调递增序列，用于幂等去重。
- `condition`：`UNKNOWN/CLEAR/CLOUDY/RAIN/SNOW/STORM`。
- `temperature_deci_c`：摄氏度 0.1 度，合法范围 `-500..600`。
- `observed_utc`：天气观测 UTC 秒。
- `ttl_minutes`：`15..360`，设备按已有 RTC 判断新鲜度；RTC 未同步时最多保留 60 分钟单调时钟寿命。
- `flags`：仅允许定义好的热/冷等布尔标志；未知位拒绝或忽略，具体规则由方案固定。

明确禁止字段：经纬度、城市、地址、账号、SSID、天气服务 key、服务商原始文案和 URL。

## 可验收标准

1. 对 6 个合法天气枚举和未知值逐一注入，设备只在宠物页创建对应氛围，退出页面后对象和 timer 全部释放。
2. 温度低于 `-50.0°C`、高于 `60.0°C`、TTL 越界、长度错误、未知版本和损坏帧均被拒绝，不越界、不更新旧状态。
3. 同一 `sequence` 连续注入 100 次，只触发一次天气变化和一次可领取互动。
4. 旧序列晚到不覆盖新序列；序列回绕策略有单元测试。
5. 快照过期后 10 分钟内恢复普通宠物；RTC 未同步、回拨和重启路径行为确定且有测试。
6. BLE 回调不调用 LVGL、不访问网络、不写 Flash；UI 只消费线程安全快照。
7. `PLAY`、`RESTORE`、打字动画、`NEEDS_INPUT`、`ERROR` 与天气交错至少 20 组序列，显示优先级和恢复结果符合本文定义。
8. 5 个 GIF 槽位的上传、选择、摘要和旧版 slot 0 协议回归全部通过；天气功能关闭时二进制行为与当前版本一致。
9. 拒绝手机位置权限、无网络、天气服务超时和 BLE 断连均不影响 Agent Pet 基本功能，且不会循环弹提示。
10. 日志、BLE 抓包、设备设置和持久化存储中不出现经纬度、城市、地址或 API key。
11. PC 模拟器可注入晴、多云、雨、雪、热、冷、过期和抢占序列，连续运行 30 分钟无对象泄漏或崩溃。
12. `sf32lb52-lchspi-ulp` 真实构建成功，记录 Flash/RAM 增量和全部警告；真机触摸、残影、刷新率与 BLE 重连标记为待硬件验收，未验证不得宣称通过。

## 资源预算假设

- 固件静态状态：不超过 256 B；不为天气功能使用 `malloc/free`。
- LVGL：常驻新增对象不超过 8 个，新增 timer 不超过 1 个；优先挂到现有宠物刷新周期。
- 固件 Flash：新增代码和常量不超过 20 KiB；新增图片、GIF、字体和音频为 0 B。
- RAM 峰值：除既有 GIF 解码内存外，天气功能新增峰值不超过 2 KiB。
- BLE：单个快照目标不超过 20 B；正常每小时不超过 1 次，类别变化可立即补发。
- 持久化：MVP 为 0 B；重启后等待伴侣重发，避免陈旧天气和 Flash 磨损。
- 性能：氛围动画目标 15 FPS 或更低，不触发全屏持续重绘；远端 GIF/打字动画运行时暂停天气动画。

## 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 来源仓库无许可证 | 代码/素材权利不明 | 只采纳产品问题与机制，协议、代码、UI、素材全部独立实现 |
| 天气服务和 API key 不稳定 | 多端伴侣不可用或成本失控 | 定义 provider 抽象、可关闭；固件不绑定服务商；无服务时正常退化 |
| 位置隐私 | 用户拒绝或产生信任风险 | 原始位置只在手机端处理；设备协议、日志和存储禁止位置标识 |
| 天气数据陈旧或乱序 | 宠物表现与现实不符 | 序列、观测时间、TTL、旧序列拒绝和过期回退 |
| 与 Agent/远端表情争夺画面 | 关键信息被遮挡 | 固定优先级；天气层可暂停并按最新状态恢复，不排队回放 |
| 5 个 GIF 槽位语义冲突 | 上位机表情兼容性破坏 | 首版天气不占槽位；可选 GIF 映射只在伴侣端配置并走既有命令 |
| LVGL 对象或动画泄漏 | 长时间运行崩溃 | 页面生命周期集中管理、单一 timer、反复进入/退出和抢占测试 |
| 天气互动过于频繁 | 陪伴感变成打扰 | 仅类别/阈值变化触发、3 小时冷却、无惩罚、可完全关闭 |

## 可行性结论

- 硬件可行：来源已在相同 SF32LB52 技术栈上实现手机上下文到 LVGL 的链路，目标仓库本身也已有 BLE worker、RTC、手机伴侣和宠物 UI。
- 软件可行：固定小包、RAM 快照和 LVGL 基本对象即可完成 MVP；不需要固件联网、动态分配或新增素材。
- 集成可行：现有时间同步证明三端伴侣可以发送上下文，现有远端表情和 GIF 生命周期提供抢占/恢复基线。
- 主要不确定性：天气 provider、移动端权限体验、真实硬件残影和与远端表情交错时序。技术方案必须先定义协议和线程模型，再决定三端伴侣的 provider 实现范围。

## 发布与回退

- 以固件编译期开关和伴侣端设置开关双重控制。
- 先完成协议解析、模拟注入、优先级和过期测试，再接真实天气 provider。
- 若移动端天气数据源无法在隐私和成本边界内稳定提供，回退为本地时间驱动的晨间/夜间氛围；不得让固件直接访问不受控公网服务。
- 关闭功能后不保留天气对象、timer、状态或持久化数据，原有宠物、GIF、Agent 状态和任务花园保持不变。

## 优先级结论

建议 **P1 试点**：进入嵌入式技术方案和小步实现，但将“隐私最小化数据契约、现有显示优先级回归、伴侣 provider 可关闭”设为开发前置条件。它是今日扫描中唯一有窗口内实质证据、与目标硬件高度一致、且能新增宠物交互闭环的创意。
