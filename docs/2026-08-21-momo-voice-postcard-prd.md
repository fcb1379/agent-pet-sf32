## 2. 问题与目标用户

### 2.1 问题

当前 Momo 能显示 Agent 状态、使用多 GIF 表情、响应触摸/IMU，并能把录音以 Opus 上行，但这些能力还没有组成一次完整的“用户和宠物互相说话”体验。实时语音聊天又需要 PAN 或持续联网、低延迟音频下行、会话编排和更严格的共存预算，当前风险过高。

用户需要的是一个比状态看板更有温度、又比实时通话更轻量的入口：把一句话留给 Momo，稍后在设备上主动听取；也能从设备录一句回复，在下一次连接时交给上位机。

### 2.2 目标用户

- 日常把 Momo 放在桌面或随身携带，希望获得轻量陪伴的用户；
- 已配对 Android 上位机，希望发送短语音给设备或收取设备回复的用户；
- 不希望设备常开麦克风、直连公网或自动播放私人语音的用户。

## 3. 产品目标与成功标准

### 3.1 产品目标

建立一个可理解、可恢复、保护隐私的异步闭环：

**上位机录制并发送短语音 → Momo 显示未读邀请 → 用户主动播放 → 可选录制回复 → 上位机收到并确认。**

### 3.2 成功标准

- 用户无需理解 PAN、网络或音频格式，在已连接状态下可用不超过 3 个主要动作完成发送、播放和回复。
- 语音传输中断不会损坏上一条有效语音，也不会破坏现有图片/GIF。
- 没有用户主动点击/长按时，设备不会播放、录音或上传语音。
- 上位机和固件均能明确显示发送中、可播放、录音中、等待上传、已送达和失败状态。
- 关闭功能后，现有 Agent 状态、图片/GIF、录音、音乐和 Pet 交互行为保持不变。

## 4. 核心创意

“明信片”不是实时通话，也不是普通录音机。每条消息由一段短语音和可选的现有 Momo 图片/GIF 关联组成，强调一次有开始和结束的陪伴时刻：

- 到达时，Momo 使用自有表情显示一个不泄露内容的未读语音徽标；
- 用户点击徽标才播放，可重复听；
- 用户长按回复入口开始录音，再次点击或达到上限后停止；
- 断线时回复保留为待发送，重连后由用户确认或自动继续，成功后给出短暂反馈；
- 消息正文不进入 Agent 状态协议，也不能触发任务、授权或命令。

## 5. 用户场景与流程

### 5.1 上位机发送

1. 用户打开已配对的 Android 上位机，进入“Momo 明信片”。
2. 用户按住或点击录音，最长 15 秒；可选关联当前已上传的 Momo 图片/GIF 槽位，不重复发送素材。
3. 上位机预览时长并允许试听、重录或发送。
4. 发送后展示传输进度；设备完整校验并原子提交后返回“已送达”。
5. 断线、取消或校验失败时显示可重试，设备继续保留上一条有效语音。

### 5.2 设备收听

1. 新语音到达后，Pet 页显示未读徽标和 Momo 邀请态，不显示发送者隐私文本，不自动播放。
2. 用户点击徽标，设备请求 Audio Manager 获得播放通道。
3. 若音乐、A2DP 或其他高优先级音频占用，UI 显示“稍后听”，不强占通道；空闲后用户再次点击。
4. 播放中再次点击可停止；播放完成后未读变为已读，但语音仍可重复播放。

### 5.3 设备回复

1. 用户在语音徽标上长按，设备先进行音频仲裁并给出明确录音提示。
2. 录音最长 15 秒；用户再次点击停止，超时自动停止。
3. 已连接且上位机准备好时，复用现有 Opus 上行发送；断线或短暂失败时保存为“待发送回复”。
4. 上位机完整校验并确认后，设备显示短暂送达反馈并清理已确认的临时回复。
5. 用户可取消未发送回复；取消和失败不能影响收到的语音。

### 5.4 无消息和异常

- 无语音时不显示空入口，不改变现有 Pet 主交互。
- 临时文件、协议版本、长度、CRC、时长或音频参数不合法时拒绝提交，并报告可诊断错误。
- 上位机版本不支持时，固件通过能力协商隐藏发送/回复入口，不反复报错。

## 6. 功能范围

### 6.1 V1 范围

- Android 上位机录制、试听、Opus 编码、BLE 下发、进度、取消和失败重试；
- 固件端语音下行分片接收、严格校验、临时文件和原子提交；
- 只保存 1 条当前收到的语音，收到新语音后替换旧语音，但必须先完整校验；
- Pet 页未读徽标、主动播放、停止、录音回复和明确状态反馈；
- 最多 1 条待发送回复；重连恢复和用户可取消；
- 复用 16 kHz、单声道、24 kbps Opus 和现有录音上行；
- 复用已有图片/GIF 槽位的标识关联，不新增来源素材；
- 能力协商、会话编号、序列、长度、CRC、重复/乱序/取消处理；
- 主机协议测试、上位机协议测试、完整固件构建和硬件验收清单。

### 6.2 非范围

- 实时双向语音通话、对讲或低延迟流媒体；
- PAN、Wi-Fi、HTTP、Docker 中继、云账号、远程公网消息和多联系人；
- 常开麦克风、唤醒词、自动录音、自动播放和环境声音上传；
- ASR、TTS、LLM 对话、声纹识别或内容审核；
- 视频、相机、连续消息历史、群聊和消息搜索；
- 新图片/GIF 传输格式；V1 只引用已经存在且有效的资源槽；
- 在未完成上位机端到端验证时把固件单侧实现标记为产品完成。

## 7. 交互和状态要求

### 7.1 消息状态

- 接收：`EMPTY`、`RECEIVING`、`READY_UNREAD`、`READY_READ`、`ERROR`。
- 播放：`IDLE`、`REQUESTING_AUDIO`、`PLAYING`、`BLOCKED`、`ERROR`。
- 回复：`NONE`、`RECORDING`、`PENDING_UPLOAD`、`UPLOADING`、`SENT`、`ERROR`。

状态组合必须有明确优先级，不能通过多个布尔量形成无法解释的组合。传输线程只投递事件；所有 LVGL 对象创建、修改和销毁必须在 UI/LVGL 线程执行。

### 7.2 手势约束

- 点击未读/已读徽标：播放或停止当前语音；
- 长按徽标：开始回复；录音中点击：停止；
- 不占用现有全屏返回手势；
- 木鱼、抚摸、多状态行为等未合入分支未来合并时，必须通过命中区域和事件优先级消除冲突，而不是依赖回调注册顺序。

### 7.3 隐私表现

- 锁屏、未解锁或没有主动操作时不播放私人内容；若项目当前没有锁屏能力，V1 至少提供“自动隐藏明信片内容”开关，默认只显示无内容文本的徽标。
- 录音中必须有持续、清楚的视觉提示；开始和结束可播放短提示音，但不得与录入内容混合。
- 上位机默认只保留用户明确保存的语音；日志不得记录音频正文、路径中的敏感名称或令牌。

## 8. 协议与数据要求

- 下行音频固定为 16 kHz、单声道、Opus，目标码率 24 kbps，最大时长 15 秒；按目标码率估算，单条压缩载荷约 45 KiB。
- 开始帧至少包含协议版本、消息 ID、总字节数、音频参数、时长、关联资源槽和总 CRC；数据帧包含消息 ID、24 位序列或等价的有界序列；结束帧触发最终校验和原子提交。
- 所有长度、序号、分片数、资源槽和枚举先验证后使用；整数乘加必须防溢出；不得由远端长度决定无界内存分配。
- 重复开始、重复分片和重复结束必须幂等；乱序策略要么有界重组，要么明确拒绝并要求重传，不能静默拼错。
- 取消、超时、断线和校验失败只删除临时文件；上一条有效语音继续可播放。
- 协议扩展不能复用 Agent 状态帧去传音频，也不能让语音内容触发命令、授权或任务状态变化。

## 9. 资源预算假设

下列是进入技术方案前的产品上限，不是已经测得的构建结果：

| 资源 | V1 上限/假设 | 说明 |
|---|---:|---|
| 单条下行音频 | 64 KiB | 覆盖 15 秒、24 kbps Opus 及封装余量；超限拒绝 |
| 当前语音 + 临时文件 | 128 KiB 存储 | 原子替换期间同时存在；不能全量常驻 HCPU SRAM |
| 待发送回复 | 64 KiB 存储 | 最多 1 条；确认后清理 |
| 传输工作缓冲 | 不超过 4 KiB | 固定容量或有界池，禁止按远端总长度动态分配 |
| 新增常驻业务状态 | 不超过 2 KiB | 不含现有 Opus 编解码器和既有音频服务 |
| 新增线程 | 优先 0；最多 1 个且栈不超过 2 KiB | 优先复用现有 BLE/音频 worker 和队列 |
| 新增固件 Flash | 目标不超过 48 KiB | 复用现有 Opus、CRC、文件和 BLE 基础设施 |
| Pet 页刷新 | 空闲不快于现有定时器；交互动效目标 20 FPS | 禁止音频分片触发全屏刷新 |

技术方案必须用真实 map/build 输出给出基线与增量；若目标文件系统没有至少 256 KiB 可安全预留空间，必须缩短时长或减少并存文件，不能把缓冲转移到内部 SRAM。

## 10. 音频与并发约束

- 语音播放和回复录音必须通过现有 Audio Manager 请求资源；禁止绕过仲裁直接打开 codec。
- 优先级建议：用户主动停止/系统安全事件 > 已在进行的通话类路径 > 用户主动录音回复 > 用户主动播放明信片 > 本地提示音 > 背景噪声测量。
- 与 A2DP、本地音乐、录音 App、噪声监测冲突时，采用“明确阻止并可重试”或经过验证的暂停/恢复，不允许同时争用硬件。
- BLE 接收回调不得做文件长写、Opus 解码或 LVGL 操作；使用固定队列把工作交给 worker。
- 文件写、队列投递、Audio Manager 和 UI 更新均需检查返回值；超时和错误必须向状态机传播。

## 11. 验收标准

### 11.1 协议与存储

1. 上位机发送 1、5、15 秒合法 Opus，设备均能提交并播放，时长误差在一个 Opus 帧范围内。
2. 对开始帧、零长度、超长、非法采样率/声道/码率、序号越界、分片重复、分片丢失、CRC 错误、错误结束帧和未知版本均有自动化测试。
3. 在传输 10%、50%、99% 时断开，重连后上一条有效语音仍可播放，临时文件可清理或安全续传。
4. 同一消息重复发送不会生成多个未读事件；已经确认的回复重复确认不会重复删除或重复提示。

### 11.2 用户闭环

5. 新语音到达后 Pet 页在 1 秒内出现未读提示，但不会自动播放。
6. 用户点击后成功播放；播放中点击可在 500 ms 内进入停止流程，界面不假死。
7. 长按开始录音有持续指示；再次点击或 15 秒到期后停止并形成一条待发送回复。
8. 上位机收到完整回复并确认后，设备显示送达反馈；失败或断线时回复仍可重试或由用户取消。
9. 无语音、功能关闭或旧版上位机连接时，Pet 页行为与 `origin/master` 一致。

### 11.3 共存、性能与安全

10. 分别在本地音乐、A2DP、噪声监测和录音 App 活动时尝试播放/回复，结果符合仲裁表且原音频路径能够恢复。
11. 连续完成 100 次短消息接收、播放、录音、回复和取消循环，无对象泄漏、线程泄漏、句柄泄漏、越界、死锁或看门狗复位。
12. 完整固件构建通过；新增编译警告为 0；主机协议测试和上位机协议测试通过。
13. 240 x 240 真机上未读入口、播放/录音状态和错误提示不遮挡返回手势，触控区域可辨识；音量安全、扬声器无明显爆音，麦克风录音可懂。
14. 未完成真机音频、BLE 吞吐和功耗验证时必须标记“待硬件验收”，不得虚报通过。

## 13. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 上位机缺少 Opus 下发 | 无法形成端到端功能 | Android 作为 V1 必需交付；先做协议向量和离线文件回放，再联调 BLE |
| BLE 吞吐不足 | 发送等待过长 | 限制 15 秒/24 kbps；复用 MTU 协商；显示真实进度；硬件测量后再定超时 |
| 文件系统空间或写入寿命不足 | 丢消息或损坏资源 | 单条上限、传输前空间检查、临时文件+原子替换、合并元数据写入 |
| 音频资源冲突 | 无声、卡死或打断音乐 | 统一 Audio Manager、显式优先级、阻止/暂停/恢复测试矩阵 |
| Pet 手势与既有/待合入功能冲突 | 误触木鱼、抚摸或返回 | 独立徽标命中区域、事件消费规则和合并回归测试 |
| 私人语音被自动播放或记录 | 隐私事故 | 默认不自动播放；录音必须主动且持续提示；无常开麦克风；日志不含音频内容 |
| 候选素材/角色版权 | 分发风险 | 仅使用 Momo 自有素材；不复制 Familybox UI、截图、声音、文案或 BMO 角色 |
| 只完成固件未完成上位机 | 功能不可用 | 完成门禁要求端到端上位机、固件、构建和协议测试证据同时存在 |

## 14. 许可证与独立实现要求

- Familybox 使用 MIT 许可证，但本 PRD 只借鉴“异步照片/语音、主动播放、录音回复、失败排队”的产品结构。
- 不复制候选的 C/Python/HTML 代码、协议字段、UI 尺寸、颜色、图标、截图、声音、提示文案或角色素材。
- 目标实现应优先复用本仓库已有 BLE、Opus、Recorder、Audio Manager、文件原子提交和 Momo 素材。
- 若工程师确需引用任何第三方代码，必须在实现方案中逐文件说明来源、完整提交、许可证、修改点和 NOTICE 处理；未经明确评审不得引入。

## 15. 可行性结论与实施顺序

### 15.1 结论

**有条件可行，建议进入子任务 2。**

硬件侧麦克风、扬声器和存储路径已存在；软件侧已有 Opus 上行、图片/GIF 下发和音频仲裁基础。V1 不依赖 PAN 或公网，因此比实时语音聊天更适合当前阶段。主要不确定性是语音下行协议、上位机 Opus 编码、文件系统实际余量、BLE 实测吞吐和多音频路径恢复，必须由实现方案和构建/硬件验证关闭。

### 15.2 推荐实施顺序

1. 冻结能力协商、下行协议、状态机、音频仲裁和存储布局；提交实现方案。
2. 完成纯 C 帧解析/校验、临时文件与原子提交的主机测试。
3. 完成 Android 端协议向量、离线 Opus 编码和 BLE 传输状态机测试。
4. 接入固件语音播放，验证真实资源和音频共存。
5. 接入 Pet 页未读/播放 UI。
6. 复用现有 Opus 上行完成录音回复和上位机接收。
7. 完整构建、自测并记录所有待硬件验收项；不推送、不合并。
